# 异步秒杀下单

## 业务约定

Redis Lua 同步预占库存、检查一人一单并登记待投递记录；Kafka 消费者在同一个 MySQL 事务中扣库存、创建订单。只有事务提交、订单可查询后，才认定建单成功。

## Kafka 拓扑与消费配置

秒杀订单 Topic 和 DLT 默认创建 3 个 Partition，消费者工厂默认使用 3 个并发消费者；生产端使用 `acks=all`、幂等生产者、批量发送和 `lz4` 压缩，消费者关闭自动提交并限制单次 `poll` 的记录数。

本地配置默认按单 Broker 运行，因此 `replicas=1`、`min.insync.replicas=1` 只保证本地环境可以启动。生产环境至少使用 3 个 Broker，并设置：

```text
KAFKA_SECKILL_ORDER_PARTITIONS=3
KAFKA_SECKILL_ORDER_REPLICAS=3
KAFKA_SECKILL_ORDER_MIN_INSYNC_REPLICAS=2
KAFKA_SECKILL_ORDER_CONCURRENCY=3
```

`acks=all` 只有在副本数和最小 ISR 配合时才提供相应的副本确认语义；Topic 同时关闭 unclean leader election，ISR 不可用时优先保持不可写，避免选出落后副本造成数据丢失。`NewTopic` 只负责创建不存在的 Topic；如果已有 `seckill-voucher-order` 或其 DLT 仍是 1 个 Partition，需要在扩容前按运维流程增加 Partition，不能依赖应用启动自动缩放。增加 Partition 后，同一 Key 的顺序范围仍只限于单个 Partition。

`Result.success` 表示本次接口调用是否成功。建单结果看 `data.state`，能否支付看 `data.canPay`，不能把 `success=true` 或拿到订单 ID 当作建单成功。

## 接口对接

以下接口都受登录拦截器保护，使用登录 token 作为 `authorization` 请求头。查询与示例支付只允许操作当前用户的订单。

### 提交：POST /voucher-order/seckill/{id}

`id` 是优惠券 ID。受理成功返回 **HTTP 202 Accepted**，`Location` 指向 `/voucher-order/result/{orderId}`，`Retry-After` 为 `1`。

```json
{
  "success": true,
  "data": {
    "orderId": "650000000000000001",
    "state": "QUEUED",
    "canPay": false,
    "message": "请求已受理，正在排队，请查询最终下单结果"
  }
}
```

前端保存订单 ID，显示“排队中”，开始查询。ID 按字符串返回，避免 JavaScript 大整数精度丢失。首次响应始终只表示受理，即使消费者恰好已完成。

库存不足、重复下单沿用 HTTP 200 + `success=false` 的现有错误格式，没有 `Location`。**本接口 `data` 已从订单 ID 改为对象，调用方需要同步修改。**

### 查询：GET /voucher-order/result/{id}

`id` 是首次返回的订单 ID。

| data.state | 含义 | 前端处理 | canPay |
| --- | --- | --- | --- |
| QUEUED | 已预占，尚未被消费者领取 | 排队中，继续查询 | false |
| PROCESSING | 已领取，尚无已提交订单 | 处理中，继续查询 | false |
| SUCCESS | MySQL 中存在当前用户的订单 | 停止查询，展示订单状态 | 仅未支付时为 true |
| FAILED | 未建单且 Redis 预占已释放 | 停止查询，展示 message | false |

SUCCESS 结果包含 `orderStatus`，使用现有定义：1 未支付、2 已支付、3 已核销、4 已取消、5 退款中、6 已退款。已取消订单仍是建单成功，但 `orderStatus=4`、`canPay=false`。

请求不存在、失败记录过期或属于他人时均返回 `success=false` 和相同提示。Redis 显示完成但数据库没有订单时返回查询异常，不凭 Redis 承诺成功或失败。

建议每秒查询一次。网络错误或前端等待超时不代表建单失败；保存 ID 并允许继续查询。只有 `SUCCESS && canPay` 才能进入支付。

### 示例支付：POST /voucher-order/pay/{id}

`id` 是订单 ID。排队、处理中、建单失败或属于他人的订单均拒绝支付。已有未支付订单才更新为已支付；重复支付幂等返回成功，已关闭订单拒绝支付。数据库行锁与条件更新协调支付和关单。

该接口仍是现有支付状态处理示例，不包含真实收银台或第三方支付接入。

## 失败与库存处理

| 场景 | 处理 |
| --- | --- |
| Kafka 发送失败 | 保持 QUEUED，按 Lua 已登记的待投递记录重投 |
| 未领取请求排队超时 | 默认 300 秒，用户锁内核对数据库后仅释放 RESERVED，返回 FAILED |
| 消费暂时失败 | 不 ACK；初次失败后最多再重试 3 次，仍显示 PROCESSING |
| 重试耗尽 | 投递 DLT；确认 DLT 写入成功后才恢复原消息 |
| DLT 核对数据库无订单 | 与建单使用同一用户锁，原子回补 Redis、移除购买标记并记录失败，完成后 ACK |
| DLT 本身失败 | 持续重试，不 ACK；库存事实不明时不提前宣布失败 |
| 同一订单重复消费或已提交后进入 DLT | 核对当前订单，不再次扣库存或回补 |
| 不同 ID 命中同一用户同一券的已有订单 | 当前请求返回 FAILED，仅退回多占库存，保留购买标记 |
| 已释放请求的迟到消息 | 识别 RELEASED，不再建单或扣库存 |
| 订单插入失败 | MySQL 扣库存和写订单一起回滚，Redis 交给重试/DLT 处理 |
| 超时关单 | 事务内关单并恢复 MySQL 库存，提交后恢复 Redis |
| 关单 Redis 回补失败 | 数据库保留 `status=4 AND redis_stock_released=0`，定时任务重试 |
| Redis 已回补但数据库确认失败 | 独立标记 `seckill:closed:released:{orderId}` 防止重复回补 |

失败结果保留 24 小时；未完成预占不设 TTL。成功以数据库为准。关单幂等标记不设 TTL，仍可能重放补偿时不能删除。

`hmdp.order.queue-timeout-seconds` 控制未领取请求的时限。任务按 `hmdp.order.message-retry-interval-ms` 扫描，发送成功后的重投间隔为 30 秒，所以超时不是精确到秒触发。PROCESSING 不按排队时限释放，避免和数据库事务并发回补。

这些保证以 Redis 数据未丢失为前提；Redis 预占与 Kafka/MySQL 没有跨系统原子事务，部署需要相应的 Redis 持久化和故障恢复措施。

## 数据库升级

新建库使用 `src/main/resources/db/hmdp.sql`。已有库在更新服务前执行 `src/main/resources/db/migration/V20261018__async_order_result.sql`。项目没有自动执行迁移的组件。

迁移把历史行标为已确认，避免未知历史关单被重复回补。历史已取消订单需单独对账，确认未回补后再将字段改为 0。历史未支付订单以后关单时，会重新置为 0 并按新流程补偿。

## 验证

接口测试：`mvn -Dtest=VoucherOrderControllerTest test`。

集成测试需要专用环境，会重建 `seckill_test` 库中的表并清空专用 Redis 的 DB 15，不能指向业务实例：

```sh
docker run --rm -d --name codex-seckill-redis -p 127.0.0.1:16379:6379 redis:7-alpine
docker run --rm -d --name codex-seckill-mysql -p 127.0.0.1:13306:3306 \
  -e MYSQL_ROOT_PASSWORD=seckill-test -e MYSQL_DATABASE=seckill_test \
  mysql:8.4 --mysql-native-password=ON
# 等待数据库 ready 后执行：
SECKILL_INTEGRATION_TEST=true mvn -Dtest=VoucherOrderFlowIntegrationTest test
docker stop codex-seckill-mysql codex-seckill-redis
```

集成测试使用真实 Redis Lua、Redisson、MySQL 事务与消费者方法；Kafka 发送使用可控 Future，验证发送失败、重复和迟到消息。

真实 Kafka 测试还需要专用 broker，使用同一套 MySQL/Redis 环境。测试会使用固定秒杀 Topic，不能连接业务 broker：

```sh
docker run --rm -d --name codex-seckill-kafka -p 127.0.0.1:19092:9092 \
  -e KAFKA_NODE_ID=1 -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://127.0.0.1:19092 \
  -e KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT \
  -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093 \
  -e KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1 \
  -e KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR=1 \
  -e KAFKA_TRANSACTION_STATE_LOG_MIN_ISR=1 \
  -e KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS=0 apache/kafka:3.9.1
# 三个专用服务 ready 后执行：
SECKILL_INTEGRATION_TEST=true SECKILL_KAFKA_INTEGRATION_TEST=true \
  mvn -Dtest=VoucherOrderControllerTest,VoucherOrderFlowIntegrationTest,VoucherOrderKafkaIntegrationTest,CacheInvalidationTest,NormalTest test
docker stop codex-seckill-kafka codex-seckill-mysql codex-seckill-redis
```

本次共通过 24 个测试，包含真实 Kafka 正常消费、三次重试后进入 DLT，以及 Redis/MySQL 库存验证。未运行依赖业务库数据的原有 SpringBootTest 数据导入测试。

`pom.xml` 的 Kafka Client 已从 2.6.0 对齐至 Spring Kafka 2.9.13 声明的 3.2.3；原组合在 KafkaAdmin 初始化时会出现 `DescribeTopicsResult.topicNameValues()` 的 `NoSuchMethodError`。

项目原有 Lombok 在本次环境的 JDK 21 上无法编译，已使用 JDK 17 验证。
