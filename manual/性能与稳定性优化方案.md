# Local Life Service 分页优化方案

基础方案更新于 2026-11-05，正文保留当时的范围和基线。2026-11-08 的代码改动和实验见[用户已发布笔记深分页实施记录](#81-用户已发布笔记深分页实施记录)。

## 1. 目标与范围

本方案依据 highlights 的《分页优化》和当前代码，解决列表组装中的重复查询，减少无用 COUNT，并通过代表性数据评估分页排序索引。

本次拟实施内容仅有：

1. 热门笔记、用户已发布笔记及关注流的作者批量查询。
2. 上述列表中当前用户点赞状态的 Redis Pipeline 查询。
3. 店铺名称列表、无坐标分类列表关闭无用 COUNT。
4. 热门笔记、用户已发布笔记及我的笔记的索引实验，有收益后再安排迁移。
5. 与上述变更直接相关的回归测试、查询次数验证和性能对照。

保留现有接口参数、页大小、返回字段、笔记 total、过滤条件、排序、权限校验、DTO 字段隔离及 Feed 游标协议。定时任务、线程池、缓存重建、L1 广播、逻辑过期、消息链路、JVM 运维和业务功能扩展均不属于本方案。

新的游标接口、延迟关联、自定义搜索方案不列入当前实施清单，仅在测量证明有必要时另行设计。点赞写入的一致性问题不在本轮读取优化范围内。

## 4. 建立基线

### 4.1 环境和数据

在专用测试环境记录代码提交、JDK、MySQL 服务端版本、MySQL/Redis 配置、连接池、CPU、内存、网络和应用实例数，固定压测工具、参数与请求分布。构建按 [README](../README.md) 使用已验证的 JDK 17，不将 JDBC 驱动版本当作 MySQL 服务端版本。

建议先使用 10 万条笔记筛查，需要时扩大到 100 万条验证深页扫描。覆盖作者分布倾斜、审核状态、相同点赞数和发布时间、重复作者、作者缺失、首屏、中间页、深页及空页。数据规模是实验建议，不是当前仓库已有数据。

测试负载包含匿名列表、登录列表、关注流、店铺名称/分类列表，以及列表查询与点赞写入混合负载。每个过滤条件的总量要足以覆盖被测深页，避免用空页误判深分页性能。

### 4.2 测量项

记录响应内容、吞吐、错误率、P50/P95/P99、每请求 SQL 次数、数据库扫描行数/排序情况、Redis 命令数及批处理调用次数。索引实验额外记录点赞写入 P95、锁等待及索引体积。

相同条件下预热后至少重复三轮，保留原始结果。COUNT 与数据查询分别计时；SQL 次数使用测试用 MyBatis/JDBC 观测验证。Redis 同时观察批处理路径和实际依赖行为，不能把 Mock 调用次数直接当成网络往返次数。

Pipeline 减少逐条同步等待，但不减少 ZSCORE 命令条数，也不保证所有命令只有一个网络数据包。Feed 还需要 Redis 扫描及 hasMore 查询，不能声称整个请求只访问一次 Redis。

不预设提升百分比。正确性和查询次数是硬门槛，延迟结果应优于或处于基线波动内；候选索引若导致可重复的明显写入退化，先分析并暂缓发布，而不是只展示查询收益。

## 5. 作者批量查询与点赞 Pipeline

### 5.1 组装流程

在 BlogQueryService 内新增私有批量组装方法；方法命名和实现由实施阶段确定，不新增公开 API。

1. 先执行原有过滤和分页，取得按原规则排序的笔记列表。
2. 结果为空直接返回，不查作者、不执行 Pipeline。
3. 提取非空作者 ID 并去重，以 userMapper.selectBatchIds 查询一次，再转换为作者 Map。
4. 当前登录用户读取一次。匿名用户将 isLike 设为 false；登录且列表非空时，按确定的 blogId 顺序将 ZSCORE 放入一次 executePipelined 调用。
5. 按原笔记顺序组装 BlogPublicDTO。通过作者 ID 填充昵称与头像，通过同位置的 Pipeline 结果填充 isLike；Map 不决定输出顺序。
6. 作者不存在保留原空字段语义，不丢弃笔记；点赞状态以 score 是否为 null 判断，不能把数值 0 当作未点赞。

使用 StringRedisTemplate 对应的字符串序列化约定构造 key/member，按当前依赖验证 Pipeline 返回结果。回调遵循 executePipelined 的返回约定，不硬编码驱动私有类型；验证结果数量和顺序，避免状态错配。

Pipeline 不提供事务快照。Redis 查询失败不得静默把整页变成未点赞，维持现有明确失败语义。该优化不改变点赞写入过程，也不保证数据库点赞数与 Redis 状态在并发下瞬时一致。

### 5.2 各入口接入

- publicPage：查询及 total 保持不变，将逐条 publicView 替换为批量组装，覆盖热门笔记和用户已发布笔记。
- queryBlogOfFollow：扫描时只收集最终选中的 Blog，扫描结束后一次批量组装；不要对每个预读批次都查作者和点赞。
- queryMyBlogs、queryPendingReviews：仍映射现有 Owner/Review DTO，不接入公开列表作者/点赞组装。
- queryBlogById：保留单条查询即可，不为复用方法额外重构详情链路。

### 5.3 Feed 必须保留的规则

保留当前页大小、扫描批大小、扫描上限、公开状态过滤及顺序。游标只推进到实际消费的 Redis 成员，不能因为批量预读而消费整批；相同 score 的 offset 必须跨批次和跨页累计。

空的可见结果不等于没有下一页；minTime、offset、hasMore 沿用当前计算规则。批量组装不能改变扫描停止点，也不能用作者是否存在来过滤笔记。

### 5.4 查询次数目标

| 场景 | 作者 SQL 目标 | 点赞查询目标 | 保留项 |
| --- | --- | --- | --- |
| 非空公开分页，匿名 | 1 次批量查询 | 0 | 1 次 COUNT、1 次笔记数据查询 |
| 非空公开分页，登录 | 1 次批量查询 | N 条 ZSCORE，1 次 Pipeline 调用 | COUNT、笔记查询及 total |
| 空公开分页 | 0 | 0 | 允许分页插件按总数短路数据查询 |
| Feed 最终有可见笔记 | 1 次批量查询 | 最终返回笔记的 ZSCORE，1 次 Pipeline 调用 | 笔记查询仍随扫描批次数变化 |
| Feed 最终无可见笔记 | 0 | 0 | 扫描、游标推进及 hasMore 查询 |
| 我的笔记、审核列表 | 不新增作者查询 | 不新增点赞查询 | 原 DTO 和 total |

## 6. 店铺无用 COUNT 清理

仅调整 ShopController.queryShopByName 和 ShopServiceImpl.queryShopByType 的无坐标分支：在创建 Page 时显式设置 searchCount=false。MyBatis-Plus 3.4.3 的具体构造器或 setter 使用在实施时编译验证。

保留 records 返回契约和页大小，不新增 total，也不修改名称包含匹配、分类条件或排序。禁用 COUNT 后越界页仍应自然返回空列表，不依赖已关闭的 total 判断。

笔记 publicPage、queryMyBlogs、queryPendingReviews 当前返回 total，继续执行 COUNT。若 COUNT 本身成为慢点，应独立评估执行计划，不能未经接口变更就移除。

本次 COUNT 改动只对合法页码评估行为兼容性，实施前补充零、负数等输入的现状测试。若需要统一返回 400 或新增最大页数，作为明确的接口校验变更另行说明，不隐藏在性能改动里。店铺 GEO 分页不进入本轮改造。

## 7. 索引实验与迁移决策

| 查询 | 候选索引 | 评估内容 |
| --- | --- | --- |
| 已发布热门笔记，liked DESC、id DESC | (status,liked,id) | 排序与扫描收益；点赞更新的写放大、锁等待和 P95 |
| 用户已发布笔记，publish_time DESC、id DESC | (user_id,status,publish_time,id) | 等值过滤与排序收益；插入/发布开销与体积 |
| 我的全部笔记，id DESC | (user_id,id) | 跨状态排序；与现有作者索引的差异 |
| 待审核列表，id ASC | 先验证已有 (status,id) | 执行计划、COUNT 与数据查询耗时 |

逐个比较加索引前后的 EXPLAIN 和实际查询结果；数据库版本支持时可补充 EXPLAIN ANALYZE。小表选择全表扫描不等于候选无效，代表性数据验证后再决策。不同状态、作者分布和页深应分别覆盖。

当前已有 (status,id)、(user_id,status,id)。后者在 user_id 固定而 status 不固定时，不能直接保证全局 id 排序；新增 (user_id,status,publish_time,id) 也不能仅凭前缀就认定可替代旧索引的所有排序用途。

liked 频繁更新，热门索引必须测混合读写。每个候选得出新增、暂缓或不新增的明确结论；没有收益则不加。当前不安排删除已有索引。

如果决定新增，后续实施单独编写手动迁移并同步初始化 SQL；项目目前没有自动迁移组件。本轮不创建迁移文件、不执行 CREATE INDEX/ALTER TABLE。上线前根据真实 MySQL 版本、表规模、磁盘与元数据锁演练 DDL 成本，记录回滚步骤。

## 8. 深分页和名称搜索的边界

offset 分页即使用上索引，仍可能扫描 offset 之前的大量索引项。第一轮只测量并记录深页成本，不承诺 N+1 和加索引能完全解决。

延迟关联可借鉴 highlights 文档，通过索引内分页 ID 减少回表，但不会消除 offset 扫描；只有证据表明回表是瓶颈时才另行纳入。届时必须保留过滤条件、稳定排序和结果顺序，不能直接复制示例 SQL。

新的游标分页会改变 current/total 等契约，不属于本轮。尤其热门列表的 liked 持续变化，需先定义跨页重复、遗漏或快照语义。现有 Feed 已有游标，保持原协议即可。

店铺名称使用 LIKE '%name%'，普通 B-tree 索引通常无法有效定位；不通过随意新增联合索引解决，也不将其直接改为前缀查询。全文索引、中文分词和搜索引擎需要独立需求与设计。

### 8.1 用户已发布笔记深分页实施记录

`GET /blog/of/user` 按作者和已发布状态计数，保留 `current`、每页 10 条和 `total`。数据查询在子查询中按 `publish_time DESC, id DESC` 分页取 ID，再按主键读取整行并显式恢复排序。空页和越界页在 COUNT 后直接返回。公开 DTO 继续通过现有的作者和点赞批量组装生成。[BlogMapper](../src/main/java/com/hmdp/mapper/BlogMapper.java) · [BlogQueryService](../src/main/java/com/hmdp/service/blog/BlogQueryService.java)

在隔离的 MySQL 8.4.11 上，用相同的 `tb_blog` 结构和 20 万条合成笔记建立两份数据。目标作者有 16 万条笔记，其中 13.6 万条已发布，包含 2,000 条发布时间为 NULL 的笔记及相同发布时间的笔记。每组交替执行三种查询，各预热 6 次、计时 30 次，返回 ID 及顺序一致。下表为串行 JDBC 查询的 P95，单位为毫秒。

| Offset | 原查询 + 原索引 | 原查询 + 候选索引 | 延迟关联 + 候选索引 |
| ---: | ---: | ---: | ---: |
| 0 | 240.098 | 2.548 | 2.262 |
| 10,000 | 344.971 | 303.408 | 4.078 |
| 100,000 | 431.976 | 455.071 | 21.239 |

深页的 `EXPLAIN ANALYZE` 显示，两个原查询都使用 `idx_blog_status_id`，读取 17 万条已发布记录后过滤作者并排序。延迟关联逆向扫描 100,010 条覆盖索引项，再按主键读取和排序本页 10 条记录。COUNT 单独测得 P95 为 13.410 ms 和 11.707 ms，分别对应原索引和增加候选索引后的表。深页仍需扫描 offset 之前的索引项。

候选索引约占 6.52 MiB。首轮发布 UPDATE 的 P95 由 0.885 ms 增至 1.096 ms，随后三轮各预热 50 次并对每组计时 400 次，P95 分别为 0.963 → 0.965、0.987 → 1.037、0.984 → 0.949 ms。复测未出现持续退化。计时范围为单连接 SQL，发布写入以更新笔记状态和发布时间的语句为样本。

索引 `(user_id, status, publish_time, id)` 已同步至初始化 SQL 和已有库手动迁移。已有库在笔记审核发布表结构就绪后执行该迁移，再部署应用。需要回退索引时执行 `ALTER TABLE tb_blog DROP INDEX idx_blog_author_status_publish_time`。[初始化 SQL](../src/main/resources/db/hmdp.sql) · [索引迁移](../src/main/resources/db/migration/V20261108__blog_author_pagination_index.sql)

集成回归通过 `GET /blog/of/user` 验证作者和状态过滤、同发布时间跨页顺序、NULL 时间、`total`、公开字段、点赞状态、非法页码和越界页。[BlogPublishIntegrationTest](../src/test/java/com/hmdp/BlogPublishIntegrationTest.java)

## 10. 验证清单

| 场景 | 验收标准 |
| --- | --- |
| 非空分页，作者相同或不同 | 只批量查一次作者，顺序与字段保持一致 |
| 作者缺失、空页 | 不丢弃有效笔记，不出现空 IN，不做无用依赖查询 |
| 匿名与登录列表 | 匿名不查点赞；登录批量查询，正确匹配每条笔记 |
| 点赞 score 为 null、0 或正常时间戳 | 按是否存在正确判断，不因数值真假误判 |
| Pipeline 异常或结果错配 | 不伪装全部未点赞，失败行为明确 |
| Owner/Review DTO 与公开 DTO | 权限和字段隔离不变，不泄露审核元数据 |
| 笔记 total、同点赞数/发布时间排序 | total 与排序规则不变 |
| Feed 同 score、跨批次、过滤空页及扫描上限 | 无提前消费，游标/hasMore 与原语义一致 |
| 店铺名称、分类列表及越界页 | 确认无 COUNT，合法请求结果兼容，空页正常 |

## 11. 发布与回滚计划

1. 保存基线数据及响应样本，先验证批量组装与 COUNT 清理。
2. 功能、真实查询次数和性能对照通过后，独立发布应用改动；保留原有 API 契约。
3. 候选索引有明确收益后，按单独迁移计划发布，不夹带删除旧索引。
4. 如批量组装导致字段、顺序、total、Feed 游标或异常语义回归，回滚对应应用变更。
5. 应用回滚不要求立即删除新增索引。若需撤销索引，在评估 DDL 影响后按迁移记录处理，避免额外风险。
