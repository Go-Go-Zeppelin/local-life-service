# 笔记审核发布

## 业务约定

笔记通过草稿、审核中、已发布、已驳回四种状态管理。使用 Spring StateMachine 2.3.1，按状态、事件、配置、动作、状态机门面与应用门面的顺序组织代码。

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| DRAFT，0 | 编辑 | DRAFT，内容及版本更新 |
| DRAFT，0 | 提交 | PENDING_REVIEW，审核轮次加一 |
| REJECTED，3 | 编辑 | DRAFT，保留最近一次驳回信息供作者参考 |
| REJECTED，3 | 重新提交 | PENDING_REVIEW，审核轮次加一，清空上次审核信息 |
| PENDING_REVIEW，1 | 通过 | PUBLISHED，同时创建 Feed 发布任务 |
| PENDING_REVIEW，1 | 驳回 | REJECTED，记录原因、审核人、审核时间 |

审核中内容冻结，已发布笔记冻结内容与状态。`version` 在每次内容或状态更新时递增，`reviewRound` 在每次提交审核时递增。编辑、提交、审核均校验期望版本，审核额外校验轮次。事务使用行锁读取当前状态，并在更新中保留状态、版本及轮次条件。

同一次提交的重复请求、同一轮同一版本审核结果的重放，返回当前结果，版本和审核元数据保持首次结果。旧轮次或相反审核结果返回冲突。审核历史字段保存最近一轮结果。

## 按文章结构阅读代码

| 阅读顺序 | 文件 | 职责 |
| --- | --- | --- |
| 1 | `src/main/java/com/hmdp/enums/BlogState.java` | 四种状态及数据库编码，空值或未知编码明确报错 |
| 2 | `src/main/java/com/hmdp/enums/BlogStateEvent.java` | 编辑、提交、通过、驳回四种事件 |
| 3 | `src/main/java/com/hmdp/config/BlogStateMachineConfig.java` | 逐条声明来源状态、目标状态、事件和 Action，配置工厂、同步执行及恢复器 |
| 4 | `src/main/java/com/hmdp/action/BlogStateAction.java` | 分别执行编辑、提交、通过、驳回的数据库动作 |
| 5 | `src/main/java/com/hmdp/handler/BlogTransitionContext.java` | 单次事件携带的笔记、操作人、命令、错误和完成标记 |
| 6 | `src/main/java/com/hmdp/handler/BlogStateHandler.java` | 创建独立状态机、恢复当前状态、发送事件、检查结果并停止 |
| 7 | `src/main/java/com/hmdp/service/blog/BlogPublishFacade.java` | 身份权限、版本轮次、重复请求处理、事务和 DTO 返回 |

例如配置中的审核通过转换如下。

```java
.withExternal()
.source(BlogState.PENDING_REVIEW).target(BlogState.PUBLISHED)
.event(BlogStateEvent.APPROVE)
.action(blogStateAction::approve, blogStateAction::onError)
```

编辑草稿和编辑已驳回笔记分别声明转换，提交草稿和重新提交也分别声明。来源、目标和动作直接放在配置中，事件枚举只保存事件名称。

审核通过的调用顺序如下。

```text
BlogController.review
  → BlogPublishFacade.review 开启事务，校验审核身份，锁定笔记并校验版本和轮次
  → BlogStateHandler.handle 恢复笔记状态并发送 APPROVE
  → BlogStateMachineConfig 匹配 PENDING_REVIEW → PUBLISHED
  → BlogStateAction.approve 条件更新笔记并插入 Outbox
  → BlogStateHandler 检查执行结果
  → BlogPublishFacade 返回，事务代理提交
  → BlogFeedOutboxWorker 后续执行推送
```

`SyncTaskExecutor` 使 Action 与 Facade 在同一线程参与数据库事务。工厂每次创建独立状态机，恢复器直接读取已锁定的 `Blog.status`。`restore()` 包含停止、重置和启动，Handler 最终在 `finally` 中停止状态机。

`sendEvent()` 返回事件是否被接受。Action 的数据库异常可能被框架捕获，因此 `onError()` 把异常写入本次 `BlogTransitionContext`。只有动作的全部数据库写入成功后才设置 `actionCompleted`。Handler 依次检查异常、事件接受结果和完成标记，异常作为运行时异常抛出，确保 Facade 事务回滚。原有业务异常和 HTTP 状态码保留。

Action Bean 只保存 Mapper 依赖。请求数据放在消息上下文中，每次事件创建新上下文。Handler 同时检查调用线程已存在事务。草稿创建直接由 Facade 初始化数据库记录，后续编辑、提交和审核使用状态机。

公开笔记查询及互动只允许已发布内容。作者通过自己的管理接口查看全部状态，审核员通过审核接口查看笔记。公开 DTO 排除版本、审核轮次和审核信息，作者 DTO 包含版本、轮次和驳回原因，审核 DTO 另含审核人。

## 权限

所有笔记管理、审核、互动及关注流接口沿用登录拦截器。现有 `/blog/hot` 允许匿名访问，其余笔记接口需要 `authorization` 登录 Token。

`tb_user.role=0` 是普通用户，`role=1` 是笔记审核员。审核列表、详情和操作每次根据当前登录用户 ID 从数据库核验角色，角色撤销立即影响后续请求。请求参数不能指定审核身份。草稿作者由登录身份设置。

审核员由数据库管理员指定。例如，确认实际审核用户 ID 为 123 后执行以下 SQL。

```sql
UPDATE tb_user SET role = 1 WHERE id = 123;
```

审核员可以审核自己提交的笔记，当前版本按审核角色授权。若业务要求作者与审核员分离，需要另外增加该约束。

## 接口

响应沿用 `Result`。无权限返回 HTTP 403，不存在或属于他人的草稿返回 404，版本、轮次或状态冲突返回 409，输入校验失败返回 400。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/blog` | 新建草稿 |
| PUT | `/blog/{id}` | 完整替换自己草稿或已驳回笔记的内容 |
| POST | `/blog/{id}/submit` | 提交或重新提交审核 |
| GET | `/blog/of/me?current=1` | 自己的全部状态笔记 |
| GET | `/blog/of/me/{id}` | 自己的笔记详情 |
| GET | `/blog/reviews?current=1` | 审核员查询待审核列表 |
| GET | `/blog/reviews/{id}` | 审核员查询审核详情及并发控制信息 |
| POST | `/blog/{id}/review` | 审核员通过或驳回 |

**`POST /blog` 的行为和返回值已经变化。** 原来直接发布并返回笔记 ID，现在保存草稿并返回包含 `id`、`status`、`version`、`reviewRound` 的作者 DTO，调用方需要同步调整。

新建草稿请求示例。

```json
{
  "shopId": 1,
  "title": "周末探店",
  "images": "/imgs/blogs/example.jpg",
  "content": "本次探店的真实体验"
}
```

草稿允许暂时留空标题和正文，提交时要求二者非空。标题最多 255 个 Java 字符，图片字段和正文最多 2048 个 Java 字符，图片以逗号分隔，最多 9 张。店铺 ID 必须为正数。编辑采用完整替换，未提供的文本字段按空字符串保存，同时须提交最新的 `expectedVersion`。

提交审核请求示例，版本取自作者详情响应。

```json
{"expectedVersion": 0}
```

审核请求示例，版本和轮次取自审核详情响应。

```json
{"expectedVersion": 1, "reviewRound": 1, "approved": true}
```

驳回时 `approved=false`，并提供 1 至 500 字符的 `reason`。审核时间和新笔记发布时间使用 UTC，Feed 使用审核通过时记录的固定 epoch 毫秒数。

热门、他人主页、公开详情、点赞和点赞列表的原路径继续可用，均过滤未发布内容。公开详情通过 `/blog/{id}` 访问，作者预览草稿使用 `/blog/of/me/{id}`。

## Feed 推送与分页

审核通过的同一 MySQL 事务中更新笔记并插入 `tb_blog_feed_outbox`，以 `(blog_id, review_round)` 唯一。Outbox 插入失败时发布状态一起回滚。

`BlogFeedOutboxWorker` 默认启动 10 秒后开始扫描，每次处理最多 20 条到期任务，轮次之间间隔 1 秒。可通过 `hmdp.blog.feed-worker-enabled`、`hmdp.blog.feed-interval-ms` 和 `hmdp.blog.feed-initial-delay-ms` 调整。

任务状态为 0 待执行、1 领取中、2 已完成。领取使用条件更新，租约为 60 秒，每次领取有唯一凭证。领取中任务超时可再次领取，续租、完成和失败更新均校验凭证及未过期租约。进程崩溃后由后续扫描恢复。

推送每批读取最多 200 条关注关系，失败后整篇重放。每次尝试按任务执行期间的当前关注关系扫描，固定本次最大关注关系 ID，后续新增关系由后续尝试决定是否覆盖。取消关注不会主动清理已写入的历史 Feed。

同一篇笔记的所有粉丝及所有重试使用事件中固定的发布时间作为 ZSet score。部分推送成功后重试不会新增重复成员或改变已有排序。失败任务保留错误及下一次执行时间，退避为 2、4、8 秒等，上限为当前实现的 256 秒，持续重试。

完成任务保留数据库记录。上述恢复针对任务执行失败和进程中断，Redis 已完成数据在后续丢失时，需要相应的持久化、备份或重建处理。

`GET /blog/of/follow?lastId=...&offset=...` 保留原参数，`lastId` 实际为毫秒时间戳上界。首次传当前 epoch 毫秒数和 `offset=0`，后续原样传上次返回的 `minTime` 与 `offset`。

每页最多返回 2 条。Redis 每批预读 20 条，数据库过滤未发布内容，每次请求最多消费 200 条。游标仅推进到最后实际消费的 Redis 成员，页面满时保留未消费的预读成员，相同 score 的 offset 跨批次、跨页累加。

响应的 `data` 包含 `list`、`minTime`、`offset`、`hasMore`。达到扫描上限时可能 `list=[]` 且 `hasMore=true`，调用方应按游标继续读取。异步推送可能晚于当前翻页到达，刷新 Feed 可读取后续到达的笔记。

## 数据库升级

新建库使用 `src/main/resources/db/hmdp.sql`，种子笔记已显式初始化为已发布，用户默认普通角色。

已有库先停止旧版本写入，在维护窗口执行 `src/main/resources/db/migration/V20261104__blog_review_publish.sql` 一次，再启动新版本。项目没有自动执行迁移的组件。

迁移新增笔记状态、版本、审核轮次、审核信息及发布时间，新增用户角色、Outbox 表和查询索引。历史笔记初始化为已发布，发布时间继承原创建时间，后续新记录默认草稿。历史 Feed 保留，迁移不生成历史笔记的重推事件。初始化脚本中的笔记和用户插入已使用显式列名。

## 验证

无需外部服务的测试。

```sh
mvn -Dtest=BlogStateMachineTest,BlogControllerTest test
```

集成测试会重建 `blog_test` 库中的表，并清空专用 Redis 的 DB 14，使用以下隔离服务。

```sh
docker run --rm -d --name local-life-blog-review-mysql -p 127.0.0.1:13307:3306 \
  -e MYSQL_ROOT_PASSWORD=blog-test -e MYSQL_DATABASE=blog_test \
  mysql:8.4 --mysql-native-password=ON
docker run --rm -d --name local-life-blog-review-redis -p 127.0.0.1:16380:6379 redis:7-alpine
# 等待数据库 ready 后执行
BLOG_INTEGRATION_TEST=true mvn -Dtest=BlogPublishIntegrationTest test
docker stop local-life-blog-review-mysql local-life-blog-review-redis
```

测试覆盖版本与轮次、权限撤销、DTO 字段隔离、公开可见性、并发编辑与提交、并发审核、Outbox 插入回滚、部分推送重试、过期领取恢复、旧凭证隔离、同分值分页、过滤空页和历史迁移。
